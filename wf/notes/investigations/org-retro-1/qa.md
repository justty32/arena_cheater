# qa 第一輪回顧：app.ts 拆檔

## 1. 過程

基準與拆檔後驗收都有明確範圍：只跑既有 E2E，不改檔、不試玩。環境修好後，b69b300 乾淨副本與拆檔後工作區均為 20 通過、0 失敗、0 略過。基準 real 1m1.717s，拆檔後 1m8.416s；只有各一次執行，不能推論效能回歸。

第一次卡在 Chromium 缺 libnspr4.so，不是遊戲斷言失敗。依 dev-env 跑安裝指令後，sudo 要互動式密碼，工具回傳非零。我停止並回 BLOCKED，使用者補齊依賴後才重跑。文件有列安裝指令，但缺少可在正式測試前攔下問題的環境預檢，所以第一次花 2m42s 得到 20 個相同啟動錯誤。

dev 已開始拆檔時，main 改派在拆檔前 commit 的 archive 副本跑基準，避免把半成品當基準。這個交接很有效。獨立埠配合輸出中的 Vite 啟動訊息，降低 Playwright reuseExistingServer 接到另一份程式的風險。但換成固定 45999 並不等於永遠不衝突；還需要伺服器身分驗證或禁止重用。

## 2. 角色卡和流程

qa 獨佔瀏覽器測試、dev 負責核心測試的邊界清楚。角色卡要求分開交代未跑、不能跑、不適用，也避免把 E2E 綠燈誇大成人工視覺已驗證。

有幾個需要釐清的點：

- 角色卡的正常入口是已通過 review 的 main REQUEST；這輪基準必須先跑，拆檔後 review 與 qa 也同時做。應明訂「重構前基準」及「純讀驗證可與 review 並行」的例外，不用每次由收信者猜。
- 角色卡寫只能寫 tests/e2e/ 與 wf/org/qa/，另允許 qa 暫存；測試設定卻自動寫工作區 test-results/。應明確把自動產物列為允許範圍，或統一改到 qa 暫存目錄。
- 新留言板要求跨部門共寫 wall.md，但原寫入範圍未列共享區。這次沒有新經驗需要轉貼，也未寫 wall；日後應先把共享區授權補齊。
- 執行層指示要求遇到未預期改動立即停下；main 後來說只看自己的範圍。應由維護者在指示來源統一並行規則，避免用較低層公告解釋高層限制。我本輪看到的工作區變動已有 main 預告，沒有當成未預期變動。
- 初始化要讀的入口多，且角色卡、org、workflow、信件有重複內容。建議角色卡當權責唯一來源，工作信只列此次範圍及例外。

## 3. 交接

main 的請求資訊整體足夠：命令、輸出位置、commit、是否可改檔、是否試玩及 Done when 都明確；依賴失敗後也有清楚的環境已修復通知。後續還主動說明 dev 已收工及 review 不改檔，降低驗證對象不穩定的疑慮。

可以再補「這次授權驗的檔案集合或內容指紋」與「Node 鎖政策版本」。僅 HEAD 不足以描述未提交的拆檔結果；我回信已特別寫明 HEAD 加工作樹修改，但這還不是可重建的精確快照。

我自己的第一次回信太長：20 個相同環境錯誤逐案列出，不利 main 快速看阻礙。建議信件固定用短摘要：狀態、對象、數量、耗時、阻礙、產物；完整案例清單另存檔並引用。環境阻擋應維持 BLOCKED，即使 runner 報 20 failed，也要分清「案例啟動失敗」與「產品斷言失敗」。

## 4. 工具和環境

本輪不缺基本執行工具；shell 能跑命令、tee 保留完整輸出，工具回傳被截斷也不影響磁碟上的紀錄。缺的是把重複程序做成受控入口，而非再多給一般 shell 權限。

建議製作 E2E runner：接受 commit 或已凍結工作樹，建立全新副本，做環境預檢，取得共用資源鎖，配置埠及產物路徑，執行測試，輸出機器可讀結果與人類摘要。副本目的地已存在時應拒絕覆寫，避免舊檔殘留；目前 archive 加 tar 的簡單命令重跑到舊目錄不會自動清除多餘檔案。

數字及案例差異應讀 Playwright JSON reporter，不解析 list reporter 的終端文字。產物應包含來源 hash、必要的未提交內容指紋、命令、exit code、起訖時間、通過／失敗／略過數及失敗階段。這項工具尚未實作，本輪也未使用新加的 subagent、fork、tools_def、board_* 工具。

## 5. 權限與安全

### 文字約束不是硬邊界

目前「只能寫自己的範圍」、「不改 src」、「只有 qa 能啟動遊戲」、「不准 commit/push」主要靠指示與自律。本輪沒有測試任何繞過方式；但一般 shell、Python 及檔案工具的能力本身並沒有由角色卡轉成檔案系統隔離。工具說明也明示 shell 不是 sandbox。mailbox 的授權文字不等於 OS 授權。

我持有的 shell、run_python 與通用檔案寫入工具對純測試角色過大。新增的 tools_def、self_tools 以及 subagent 能力若可建立任意程式入口，也必須納入同一個執行邊界；只限制工具名稱不夠。board_* 是協調介面，不是資源互斥或權限控制。這些是能力風險判讀，不代表已實測可以逃出任何現有 kernel 限制。

### 本輪靠判斷守住的地方

sudo 那次我把非零輸出視為權限決定，不嘗試輸入密碼、改 sudo 設定、換其他安裝來源或用私有函式庫繞過。直接回報缺少的依賴與需管理員處理，這與專案規則一致。

另外，乾淨副本的 node_modules 是指向工作區的符號連結。對既有測試執行很方便，但不是隔離：若在副本執行安裝或惡意腳本，仍可能透過連結改動共享依賴。因此「乾淨副本」只描述原始碼來源，不代表執行環境唯讀或安全。

### 如果開 E2E 下屬

我會給它單次任務的唯讀原始碼快照與唯讀依賴、獨立可寫的 artifacts 和瀏覽器 profile，禁止存取主工作樹、.git、其他部門暫存、agent stack、使用者憑證及管理員能力；只允許必要的 loopback 網路，不開外網。還需限制執行時間、程序／記憶體及產物大小，任務取消或逾時時清掉整組子程序。

現有 subagent schema 有 workspace 與資源限制，但 workspace 指定本身不是路徑 ACL；資源限制也需看 daemon/cgroup 支援，不能當成整體 CPU 或檔案隔離已成立。需要由維護者提供 OS 層 sandbox、唯讀掛載、不同帳號／權限及網路隔離，並禁止子代理透過工具重建無限制執行入口。不能只靠父代理在提示詞裡寫「不要碰」。

### Node 鎖與其他資源

flock 適合先解決合作代理同時啟動 Node 工作的問題，但它是 advisory lock：未經 runner 的命令仍可不拿鎖。鎖應包住整個命令生命週期及清理，不能主命令一退就留下背景伺服器繼續跑。

更重要的是政策字面有歧義：「同時只有一個 Node.js 程序」與提供的 npm/Playwright 範例不相等。一次 E2E 任務通常就會啟動 npm、Playwright、Vite 等多個 Node 程序；flock 序列化的是頂層任務，並不把程序數降為一。建議請使用者確認是否真正要「同時一個 Node 任務樹」。若要求字面只有一個程序，現行 E2E 架構需要重設，不能聲稱加鎖便達成。

瀏覽器測試可先共用同一個任務鎖與固定 worker=1，埠則由 runner 配置並驗證目標身分。若將來需要分開資源，應有統一 lease 管理，不由每個代理自行挑固定埠；有多把鎖時要有固定取得順序，避免死鎖。先維持簡單的全域任務鎖，比現在就開平行試玩更安全。

## 6. 給組織的建議

優先釐清 Node 政策的「程序」和「任務樹」，把鎖包進唯一 runner；不要把協作鎖說成硬限制。其次把環境預檢、快照、埠、結構化報告整合起來，讓 qa 把注意力留給差異及缺陷，而不是重複拼命令。最後統一角色卡的自動產物、共享留言區與並行 review 例外，並由維護者評估可真正執行的權限隔離。

這輪最有用的是先保留可重跑的綠燈對照組，以及 main 明確說清楚何時工作樹已凍結。最不應延續的是依賴每個代理自行記住一串限制，卻把它當成系統已經保證安全。
