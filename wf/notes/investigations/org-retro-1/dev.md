# 第一輪回顧：app.ts 拆分

## 1. 過程

順的地方是任務邊界明確：只拆 app.ts、不改行為、七個模組逐塊驗證，沒有一邊拆一邊加功能。低耦合的 fighter-details 先搬，後面用共享 session 與明確 callbacks 接線，最後原始可執行行的正規化比對，幫助確認沒有漏搬。main 最終告知 review 通過、qa 20 案全綠；這是他們的驗收結果，不是我自己跑的 E2E。

卡住主要不是程式，而是共用工作樹的變動規則。對話中實際有兩次停工事件：第一次發現 SESSION-LOG／WAIT_USER 改變，第二次取得續做授權後發現 org README 也改變。第一次我寄了兩封 BLOCKED（第一封漏填原信 in_reply_to，第二封補正），加上第二次的一封，可能因此看起來像三次。不是三個獨立的停工事件。

上層規矩要求發現不是自己造成的意外變動立即停工，但一開始沒有定義多部門同一工作樹中哪些變動屬預期。main 先只豁免兩個狀態檔，隨後另一份組織文件變動，照該次明確指示就必須再問。後來改成只盯自己的寫入範圍，才符合這個協作模型。我的改進空間是第一封直接把「是否以部門範圍作為停工邊界」一起問清楚，並一次正確回原信，避免來回。

實作中 session 搬移腳本對箭頭函式型別、spread 與註解後的識別字處理不完整，造成型別／引用錯誤。是我過早使用自製文字掃描器，非需求不清楚；tsc 在本塊擋下，修正後重跑才進下一塊。之後應選更小的精確替換，或正式語法工具，不擴大臨時解析器。

## 2. 角色卡和流程

- 初讀角色卡的第一件工作包含拆 tests/e2e/arena.spec.ts，但它同時是唯讀範圍；後來角色卡補明先與 qa 協商，這個修正必要。任務清單不應被誤認成寫入授權。
- dev 的 Done when 是 test/build/code map；refactor 又要求 testing，其中包含 E2E。後來角色卡明確 E2E 由 main 轉 qa，解決了「dev 完成」與「整體可提交」混用。建議保留這兩個完成層級。
- 一般工作流要求開始先寫 SESSION-LOG，但 dev 沒有寫入權。應在部門入口明說由 main 維護共用狀態，部門用信件交接，不讓每個部門自己推導例外。
- src/ 可寫，但角色卡又寫不改產品 README。src/arena/README.md 是程式導航，不是產品入口；這輪 main 明確指定更新，沒有阻擋。角色卡可以直接區分根目錄產品 README 與 src/ 內技術導航。
- moving-things 的「清舊的前先確認來源已 commit 且 push」較像跨 repo 搬檔，不適合直接套在本地函式抽取；否則與禁止 dev commit/push 衝突。此次沒有刪原檔，只抽函式；應明定該條的適用範圍。
- 角色卡、system、org、testing、refactor、dev-env 有重複規則。建議保留各自入口，但將可寫範圍、執行授權與驗收責任集中一份可供工具讀取的契約，md 只解釋。

## 3. 交接

main 的實作信資訊足夠：基準 commit、只動哪個熱點、每塊 test/build、不跑 E2E、具體 Done when 都有。把我試運轉的七模組草案直接變成固定清單，也讓我必須為原本只是一個方向的架構負責；這次可行，但以後可以允許先低耦合抽取，再依實際相依提報調整，不必為檔名達標硬建抽象。

缺的資訊是並行變更契約，以及驗證資源鎖規則；鎖是本輪後段才建立，我前面未加鎖的測試不是拒絕遵守，當時尚未收到規則。

我的 DONE 太長，重要訊息埋在敘述裡。下輪建議信件只放結果、改動範圍、驗證摘要、風險與下一棒；逐塊 log 對照與詳細檔案統計存成部門成果檔。只有需要長期保留的報告放 wf/org/dev/，臨時日志仍放 /tmp。BLOCKED 必須一次回正確 reply_to／in_reply_to，不先寄一封獨立狀態又補一封。

## 4. 工具和環境

apply_patch 在 shell 中不存在；我試了一次得到 command not found，沒有安裝或繞過，改用現有 edit 工具。編輯能力並不缺，但啟動環境的慣用工具提示應與實際可用工具一致。

反覆程序是每塊 npm test、npm run build、保存兩份 log、讀退出碼、列案數。值得做成受控的驗證工具：取得 Node 執行租約，按順序跑測試／建置，輸出結構化結果與 log 路徑；任一失敗不能被後續成功的命令掩蓋。這輪 shell 使用 a／b 保存退出碼再 echo，但整條命令最後仍可能回 0，不能只看 shell 的最末 exit code。

也值得有唯讀的「部門範圍變更快照」：保存開工時 hash／git diff，收尾對照，區分原有髒檔、自己改動、外部變更。git status 只顯示檔案層級，不足以判斷同一檔是否被另一個 agent 改寫。

本次新加的 subagent、fork、tools_def、board_* 只有閱讀工具定義，未呼叫，沒有開下屬或新增工具。

## 5. 權限與安全

### 目前主要是文字約束

從我看到的工具介面，shell 明說不是 sandbox，run_python 也可執行標準庫程式；read/write/edit/copy/move/remove 可接受絕對路徑，沒有在介面上聲明部門路徑 allowlist。我沒有測試越權，也不能證明底層完全沒有額外限制；但不能把角色卡當成已存在的強制隔離。

「只寫 src/ 等路徑」「不能 commit／push／切分支」「不能跑 E2E／server」「不碰別人的 stack」目前都主要靠遵守文字。shell 理論上能執行這些命令，或啟動其他程式間接做。只收走一個顯眼工具也不夠，因為通用 shell／Python 有同等能力。網路、憑證、git hooks 和外部副作用若仍可達，也不能由文字宣稱已阻擋。

### 工具權限過大處

self_tools 可增添工具，tools_def 可定義工具，subagent 能變更其工具與設定；若沒有底層政策，這些都是擴張能力的入口。fork 複製目前工具與對話，還有權限／敏感內容傳遞風險。這是能力分析，並非這輪實測的攻擊結果。本次沒有使用這些新工具。

單獨禁用 self_tools 還不夠：必須讓所有新工具及子程序服從同一套不可由 agent 改寫的政策。工具描述的安全承諾也應與實際執行層分開。

### 這輪依靠判斷的邊界

我沒有改 arena.spec.ts、沒有啟動 server 或 E2E、沒有提交，都是靠角色卡與自己的判斷，而不是看到工具拒絕。src/arena/README.md 的導航更新也靠理解其歸屬和 main 的明確授權。兩次並行變更停工是在遵守安全規矩，但揭露了安全規矩若沒配合多 agent 模型，會產生大量不必要中斷。

### 下屬應如何限制

這輪角色卡只允許開發第一階段 1 個，因此現在不該自行開下屬。若未來正式開放，我想要：獨立工作樹或只讀輸入快照；只給單一任務所需檔案的可寫副本；回傳 patch／測試結果，由父層審核合入；獨立暫存、期限、預算與可撤銷租約。不要直接繼承整段對話、全部工具、所有憑證。

現有 subagent 的 limits 有記憶體、CPU 秒數等限制，但文件明說許多是每個子程序的限制，不等於 agent 任務的累積資源上限。user 參數可用另一帳號、mem_total_mb／procs_total 視 cgroup 支援；ws 只是預設工作目錄，不是檔案系統牢籠。單靠工具清單與 ws 不能保證限制存取路徑。

需要的硬限制是：執行層管理的 mount／filesystem sandbox 或 OS 身分與 ACL；限制寫入 allowlist、隔離 git metadata 與其他 stack；不給網路／憑證時真正在網路和環境層切斷；所有子程序不可自行解除。並提供可稽核的寫入紀錄、拒絕原因與任務層資源配額。這些應由 aos／執行環境擁有者確認能力，不由 dev 自己改 $AOS_HOME。

### flock 與資源分配

一把共享 flock 是簡單可行的「協作任務互斥」，等鎖比測試互相拖慢好，程序結束後通常能自動釋放。但它是 advisory lock，忘記加鎖就能繞開；長駐 dev server 會長時間占用，排隊狀態也不透明。

更關鍵的是「一次一個 Node.js 程序」和「一次一個 Node 任務」不是同一件事：flock npm test 並不阻止 npm 啟動 vitest，或 vitest 產生多個 worker；本輪測試輸出曾顯示 11 workers。故這個方法不能保證全機只有一個 Node 程序。我只看到命令與測試輸出，沒有對當時程序樹做量測。

建議先釐清使用者真正要保護的是並行建置任務數、總 CPU／記憶體，還是真的程序數。若是前者，集中排程／租約並限制 worker 數更合適；若真要求程序數 1，現有 npm 工具鏈本身可能不符合，要由環境負責人設計可行執行方式，不能把 flock 當已完成硬保證。

## 6. 給組織的建議

1. 開工信固定包含：檔案範圍與排他權、基準、驗收分工、資源租約、預期並行變動；不要靠中途出錯才補例外。
2. 優先做強制檔案／執行權限邊界，再談開下屬。對通用 shell／Python／自加工具採同一底層限制，不能只禁某個工具名稱。
3. 定義「dev DONE」不等於「可提交」；review、qa、integration 各自留下可觀察的驗收狀態與來源。
4. 保留逐塊驗證，但做成結構化工具與 log 索引；信件保持短，細節外放，避免重複寄回報。
5. 先釐清 Node 鎖要限制任務還是程序，再請 aos 窗口評估排程／cgroup 等硬資源政策；不要直接把 advisory lock 說成強隔離。
