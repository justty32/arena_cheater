# 第二輪回顧：工具審查、權限與資源

## 審查過程

三次才收斂，主因不是門檻變動，而是第一版把「正常流程會清理」當成了「取消和錯誤路徑也會清理」。第一輪發現 stop 例外會中斷清理、SIGTERM 未處理及 scope 狀態判斷過寬；第二輪修正後，仍有 SIGTERM 非同步拋例外與 Popen 位於清理保護之外的窗口，另一支工具則在清理未完成時繼續 build。第三輪把取消改為旗標、完整涵蓋啟動與清理，並在清理失敗時停止後續步驟，才符合原本的一次一件工作要求。作者補的 mock 測試能對準這些路徑；我只讀測試，沒有執行，不能將審查通過當成實測通過。

開工信若先列出不變量和故障矩陣，應能減少來回：持鎖直到工作樹回收；啟動失敗、逾時、SIGTERM、stop/show 失敗都要有結果；清理失敗不得開始下一件工作；scope 查詢不確定不能當成已清理。同時明定 SIGKILL、systemd manager 故障及惡意逃離 cgroup 是已知限制，不要求 Python finally 保證不可能的事。不過事前標準不能取代逐路徑審查，也不能保證一次通過。

角色卡建議補上「工具審查」入口，要求派工附版本或 diff、威脅模型、阻擋條件、已知限制、作者實跑證據；審查報告區分靜態推論與已驗證結果。可把這次反覆出現的取消、清理、鎖生命週期項目收進 checklist。這些是建議，本次沒有修改角色卡。

## 權限與安全

本輪只讀不跑完全依賴文字自律，並非現有工具擋得住。調查文件指出檔案工具可用絕對路徑，shell/run_python 不是沙箱，且可修改自身設定或透過其他能力取回權限。因此「拿掉 shell」或 guard hook 不能單獨稱為安全邊界。

我建議 review 採專用最小能力定義：專案快照唯讀掛載，只開 review 產出與暫存目錄可寫；預設不給網路、憑證、stack 設定及 daemon 控制權。需要 git diff 等命令時，走受限沙箱；所有其他讀寫工具也必須受同一政策限制，不能只包 shell。aos-sandbox 目前是逐工具包裝，單靠 ws_write 也不足以提供部門路徑白名單，所以這是待設計方案，不能宣稱目前已達成。

工具的固定命令、參數白名單和 log 路徑限制可減少誤用，但 npm 執行的是專案程式；workspace snapshot、symlink 或相依套件都不是安全邊界。systemd scope 主要管資源與回收，不隔離主機檔案、網路或憑證。同 uid 能改 cgroup 的情況也不屬於抗惡意保證。工具實作及其定義應由不同於執行者的權限保護，避免審過的工具之後被自行替換。

## 給組織的建議

文字約定適合分工、驗收與例外說明；「不能寫、不能執行、不能超額」若是使用者真正要的保證，就應由 agent 無法改動的邊界執行。先明確區分防失誤與防惡意兩個目標，再請使用者決定成本，不直接替使用者選擇架構。

資源應分成准入與配額：Node 一次一件是排程規則，flock 只約束合作的呼叫者；MemoryMax、CPUQuota、TasksMax 是 scope 內的上限。多個各有上限的 scope 仍可能累積超額，因此還需要上層共用總額與中央准入。建議排隊能回報持有人、等待狀態與取消結果，且未確認回收前不得釋出執行名額；不要讓每個 agent 各自持有一份看似安全的額度。

## 想請 eca-aos 回答或考慮

能否提供不可由下屬修改的角色能力模板，讓檔案、命令、自我設定、子 agent 和跨 daemon 控制都遵守同一邊界？逐工具沙箱如何避免遺漏未包裝的通道，又如何讓 review 只寫指定的兩個產出目錄？

資源方面，能否以任務樹為單位做中央准入，並在共同父層設總額、保留可查詢的排隊與清理狀態？若在同 uid 下只能防失誤，應明確標示，並說明提升到抗惡意隔離需要哪些外部權限。

最後，信件寄件人驗證、代辦授權與工具版本識別能否納入設計？否則受限 agent 可透過未驗證的信件請有權限者代做，或使審查結論與實際執行版本脫節。這些請 main 彙整詢問，尚未代表組織決策。
