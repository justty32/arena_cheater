## 三份的共識

- **工具是「半硬」的**：走工具的那條路，鎖和 scope 真的會生效。但 shell、run_python、同一個 uid 都能繞過去，所以這只能叫「合作 agent 的防失誤」，不能叫隔離。說明權限時，要標明是靠哪一層擋的：文字約定、工具檢查，還是 OS 邊界。
- **真要限制下屬**：
  - 用專用的最小定義，不要拿通用定義來一支一支刪工具。
  - 讀和寫的入口都要逐支包進 sandbox，stack 不能可寫。
  - 會讓能力恢復的路徑要全部關掉，例如 self_tools、self_hook、subagent、agents_ctl、agent_def。
  - mailbox 也要收窄，免得下屬請別人代做。
- **三輪才收斂**：原因是首版沒有涵蓋取消、啟動、清理這幾條路徑。以後開工信先列出不變量和故障矩陣，寫明哪些情況算阻擋、哪些算已知限制，例如 SIGKILL、manager 故障。
- **資源要分兩層**：准入管「同時幾件」，現在用 flock；配額管「一件用多少」，現在用 scope。兩層不能互相取代，而且多個 scope 加起來仍可能超量，所以上層還需要共用的總額。另外缺少可觀測性：沒有 memory peak、OOM 事件和限流量，就沒辦法合理調整參數。
- **因果修正**：下屬在 mem_mb=2048 時遇到 EAGAIN，父代理在 4G scope 下正常。但兩邊不只差在這一個變因，不能斷定是 rlimit 造成的。
- **長任務要在每個階段交界讀信**：這次取消信晚到，就是因為 qa 中途沒有讀信，等到整件事做完才看到。
