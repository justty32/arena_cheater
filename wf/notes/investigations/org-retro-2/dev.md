# 第二輪回顧：arena_verify 的權限與資源

## 1. 做工具的過程

tools_def new/check 能順利產生 entry、schema、metadata，self_tools add 能立即註冊工具，適合把固定驗證程序收斂成一個介面。check 的 sample 會真的執行，不是乾跑；第一次使用前應先知道它會拿鎖、啟動 Node、寫 log。check 通過代表工具格式合格，不代表取消、程序清理、權限邊界已經安全。shell 沒有 apply_patch 時改用既有 edit/write 即可，不應把工具被拒絕當成需要繞過的障礙。

兩次 review 退回主要是我的設計遺漏，不只是標準未先講清楚：第一次把正常 timeout 的 finally 誤當成一般終止也會執行，漏掉 Python 預設 SIGTERM 不走 finally；清理階段也應彼此隔離，不能因 stop 或 reap 例外而跳過後續查詢。第二次只在最後用 ok=false 表示清理失敗，漏想「下一步是否能安全啟動」：test 未收乾淨就跑 build，即使最終回失敗，也已違反單一 Node 工作限制。

目前改為 SIGTERM 只設旗標、輪詢後在鎖內清理；stop、launcher 終止/reap、scope 查詢分段保護；清理沒確認成功即略過 build，JSON 寫明原因。mock 已覆蓋 stop timeout、查詢例外、scope 未回收，以及 test 失敗但清理成功仍跑 build。設計前若有一張共同驗收清單，應能更早抓到這些問題：成功、一般失敗、timeout、取消、清理失敗、後續步驟准入與寫入邊界。這不是用清單取代審查，而是讓首版先對齊契約。

## 2. 權限與安全

經工具執行的 test/build，現在固定命令、自動取得共享 flock、每步獨立 systemd scope，套用 MemoryMax=4G、CPUQuota=400%、TasksMax=256；不提供任意 command，也不在 systemd 不可用時降級執行。log_dir 解析後只接受 /tmp/aos/arena_cheater/ 內的位置。這些對正常工具呼叫已有程式與作業系統層的約束，不再只靠模型記得加參數。

但約束範圍只是這條執行路徑。flock 仍是自願協定，shell/run_python 可以直接開 Node；同 UID 可主動移出 cgroup。工具執行 npm scripts 也不是檔案沙箱，沒有把專案其他部門檔案變唯讀。log_dir 的 resolve 檢查不防同 UID 惡意並行置換符號連結。工具本體遭 SIGKILL、manager 故障等情形，仍不能絕對保證清理。角色卡、部門邊界、不得開 E2E 等規則，若未加相應邊界，仍靠合作遵守。

「工具半硬、shell 可繞過」可以作為防疏漏的過渡方案，但不能宣稱已隔離下屬。我建議分兩層表述：可信任的協作 agent 用工具減少失誤；需要真的限制能力的下屬，用最小專用定義與沙箱執行入口。是否移除現有開發能力、採哪種隔離強度，應由 main 和使用者決定，不在這輪自行收權。

讀過 aos-permissions.md 後，我認為 dev 開下屬至少應做到：

- 任務先明列唯讀/可寫路徑、交付物、允許的驗證與資源預算；固定程序直接用工具，不再開 agent。
- 若宣稱硬限制，就不能只設 ws 或刪 shell；需用專用最小定義，排除 self_tools、self_hook、任意寫 stack、未包沙箱的程式執行、再開下屬與跨 agent 控制等能力恢復路徑。
- 可寫範圍以 aos-sandbox 的 rw/ro 配置落實，stack 不可寫且不可落在可寫 ws 裡；工具本身逐支確認是否包住。ws_write 有已知 stack 命名/位置坑，不能直接當完整邊界。
- 只留必要讀取、交接與受限寫入介面；信件請求不是授權，收件者也要核對原任務，避免透過請別人代做擴權。
- Node 驗證只交固定受控工具；若不能關閉其他程式入口，就明講只是協作約定。rlimit 不是整個 agent 的總額；要限制整群資源需另外確認 cgroup/委派前提，不能把設定鍵存在視為實際生效。

這輪未開下屬，也未實作或驗證上述完整沙箱組合；最低配置仍需 eca-aos 協助驗證。

## 3. 資源分配

flock 加 systemd scope 的分工清楚：flock 限制同時幾件 Node 工作，scope 限制其中一件工作的程序樹，二者不可互相代替。實測能取得獨立 cgroup，看到 MemoryMax=4294967296、CPUQuotaPerSecUSec=4s、TasksMax=256；一般完成、timeout、SIGTERM 都驗過回收。清理失敗時禁止後續工作，必須是資源准入規則，不只是結果報表欄位。

4G、400%、256 對目前 116 案核心測試和 build 可以正常運作，但只能說這個基準可用，不能說已證明最佳。這輪未量峰值記憶體、CPU 用量與 tasks 高水位，也未證明 OOM/配額撞限時的所有行為。400% 是最多約四個 CPU 的時間份額，不是固定綁四核心；MemoryMax/TasksMax 也不是保留額度。這是上限，不是公平分配或整機容量保證。

目前每次只有一件 Node 工作，這組上限可先保留做防失控基準；若之後准許多件並行，應先量整機與 agent/瀏覽器/LLM 等其他工作負載，再設上層總額，不能把每件 4G 直接乘上並行數而不看主機容量。核心測試/build 與瀏覽器測試可能需要不同 profile；是否調整數字應交 main/使用者，不憑這輪少數成功樣本替他們決定。

## 4. 給組織的建議

把「格式通過」「一般驗證成功」「取消/故障路徑通過」「隔離邊界成立」分開標示。固定工具的審查模板應要求：鎖涵蓋完整生命週期、每段清理即使出錯仍繼續嘗試、無清理證據不得啟動下一件、取消不留後續步驟，以及可機讀的失敗/略過原因。外層 runner 的終止寬限也必須留得下清理時間。

權限聲明應標明是文字協定、工具檢查、還是 OS 邊界；採用工具後不要把整隻 agent 都算成受限。工具新增/修改/註冊也是能力變更，這輪有 main 授權不表示以後可以自行擴權。先有明確的專用下屬定義，再考慮擴編，比在通用定義上逐支刪工具可靠。

## 5. 想請 eca-aos 回答或考慮

1. 能否提供已驗證的「唯讀分析下屬」與「限定路徑開發下屬」最小定義，明列能力恢復路徑、stack 保護、逐工具沙箱配置與已知漏洞？若須多個工具分別包住，能否有完整性檢查避免漏一支？
2. 工具 runner 在取消/timeout 時，是否能提供統一的 SIGTERM、清理寬限、最後 SIGKILL 與整個 cgroup 回收契約？鎖與 scope 的生命週期若都由可被殺的工具程序維護，外層死亡仍有缺口，是否能交由 supervisor 持有？
3. 能否提供任務級資源入口：把共享鎖、scope、整群總額與排隊整合，並回報 memory/tasks 高水位、OOM、配額原因及清理證據？不要把 per-process rlimit 誤呈現成 agent 總額。
4. 同 UID、/mnt/c drvfs 與目前未驗證的委派配置下，實際能承諾的隔離等級是什麼？若無法防主動逃脫，是否需要不同信任層級或受控外部執行服務，而非只在工具名稱上宣稱安全？

以上是建議與問題，不是本輪已採用的系統設計；我只完成 arena_verify 的授權範圍，沒有修改 aos 本體或其他部門設定。
