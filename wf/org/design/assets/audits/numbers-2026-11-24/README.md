## 結論

現況不是「V3 數值已套用但有幾個漏改」，而是快版戰鬥尺度加 V2 卡牌資源、投擲／法術絕對傷害，再加已授權捕獸夾的混合版。多數來源差異是明示延期，不是工程回歸。最危險的半套遷移是只把體力上限改成 V3 的 10：目前一般攻擊耗 12，移動也要求至少 12，標準鬥士將無法自主移動或出手。

產品說明大致跟程式一致；真正需要整理的是舊規格入口、需求表落後與規則／卡面字串重複。不要在架構重構時順便修平衡。先抽出「保持行為不變」的現值表，通過回歸，再另開 V3 遷移。

## 優先風險

D01~D19 涵蓋五種已明定鬥士的生命／拳傷／體力／移速／尺寸、狼象特性、現有持用武器、盾、倒地與恢復。程式以倍率算持用傷害，來源表是傷害欄；若不先決定與角色拳傷的關係，不能簡單把倍率改成那個數字。投擲傷害和持用傷害須保持不同欄位。距離必須區分中心距、體表間隔、起手距及命中容差，cm 統一轉 m，直徑統一轉明確的半徑欄位。

新拳傷1搭配既有四捨五入／最小1，會讓1.2倍背擊與半傷格擋失去部分區別；這是遷移影響，不表示現在程式寫錯。慢回10/s、快回22/s、防禦耗6/10、移動門檻12與控制時間都要連同新體力尺度評估。不能只照一個係數縮放，因為短斧原本18、來源1.5，其他武器耗體也不是同一倍率。

D16 記錄舊spec「體力不足可休息或移動」比程式低於12禁移更寬。D20~D21 記錄文件版本風險：V2入口仍稱外部404，舊spec狼快鹿未定；需求V2S10/V2S11的note仍說其餘後續，但謹慎思考／直覺已落地，V2S05仍是未命名補石。各切片14/18/22張是歷史，不應直接判為錯誤；現況18種36張已有產品文件說明。需求表不是執行數值庫，也未全面遷入V3。

D22~D25 特別保留「相符／未定」而非硬列錯誤：捕獸夾1傷3秒與原文一致，半徑0.55、武裝0.6、壽命12是現值；五色分布、每牌2張、棄牌補牌冷卻等為既有預設。不要把捕獸夾授權擴張為全部預設已批准。程式規則和卡面／log字串寫兩次同一秒數，是未來漂移來源。

## 單一來源方案（提案，未建檔）

建議唯一人工維護的「啟用中玩法數值」資料表放 `wf/org/design/assets/data/arena-balance.json`，契約 wf-table/1。design 保管數值、單位、來源和授權；dev 保管載入器、型別與規則運算；integration 負責提交；main 負責收使用者裁示。此路徑符合目前 design 寫權且能由 tabledb 編輯。若 dev 認為正式 runtime 資產應位於 `src/arena/data/`，須先由 main 定義共同資料所有權，不能形成兩份手填權威表。

每列以穩定 `id` 辨識一個參數，例如 `fighter.wolf.maxHp`；欄位建議 `id, domain, entity, parameter, value, unit, source_path, source_locator, source_revision, decision, rationale`。value 使用原生 number／boolean／有限 enum，不把數字埋在中文敘述，不把 x/未定寫成0。unit 明定 hp、stamina、m、m/s、s、ratio、count；費用可拆 generic 與各色欄位的參數。資料表只載入現行啟用值，未批准V3候選留在本盤點或另外提案表，不與runtime混讀。

建議 dev 評估 Vite/TypeScript 的靜態 JSON import，經唯一 `balance.ts` 轉接器驗證 schema 並組成 typed readonly maps，遊戲／UI都透過它取值。不是每tick找row，也不在瀏覽器跑Python或HTTP fetch讀wf。現有 tsconfig 未顯式設定 resolveJsonModule，是否加設定由dev檢查；建置若不適合直接import wf，可改為build-time產生TS檔，但產物必須標示不可手改、生成結果／hash由CI檢查，不能把產物當第二個可編輯來源。

文件不再手寫完整數字副本；由同一表產生可讀參考頁／卡面格式化文字，spec留公式、語義、取捨與來源差異，docs引用產生頁及操作語義。更新數值時一併產生文件；若產生頁入git，CI驗證無漂移。卡面描述中的傷害與秒數也要套模板，並讓log使用同一數值。模擬測試必須保留獨立的已批准關鍵期望值／守恆案例，不能所有assert都從同一表讀值而測不出錯誤改表。

邊界：只把可調玩法參數納入；數學常數、RNG演算法、epsilon、陣列索引、CSS像素與紙娃娃圖形座標不是同一類平衡參數。classic另namespace或另表，第一步不重配經典。固定步進與結算上限可集中為規則參數但標為技術契約；修改需重播與時間邊界驗證。演出引用規則的0.35秒起身時間可共用規則來源，但畫法仍歸scene/art。

## 遷移範圍與 art

建議拆為先資料治理、再玩法遷移，而不是直接選新數字。第一階段抽現值與消除重複，必須相同seed／指令／時間得到原結果，覆蓋牌庫順序、付款、傷害取整、飛行、陷阱與結算。純數值抽取不需要先開art，不做尺寸或視角變更。

V3完整數值遷移至少跨鬥士基礎表、武器公式／耗體／CD／射程、恢復與防禦、狼象效果、控制時間、碰撞尺寸和演出；最後要測法術與投擲的相對影響、擊殺補石節奏及180秒平局率。不是改五列SPECIES就完成。固定seed批量戰局可提供戰長／勝率／介入次數，但不能替代真人趣味判斷。

一旦納入V3直徑1m、武器外觀尺寸、PDF上視或整場比例，應在切片開始前開art，與dev一起確認視覺接觸與碰撞／射程一致；至少驗桌面、320/390px、腳部遮擋與陷阱並排辨識。即使不換視角，半徑0.32~0.46改0.5也是碰撞／視覺尺度工作。不要把PDF上視當作V3數值遷移自動授權。

「V3完整數值」與「V3所有內容」應分開：未實作武器／法術、惠惠選角、種子、巨大縮小及其他狀態不因整理數值自動加入；野獸和地形依原文仍延期。狼象固定加值是已存在的V3來源要求，不需再問原文是不是+3/+2，需問的是遷移時機與混合尺度是否接受。

## 待決問題（選項與建議，尚未採用）

第一個決策是遷移批次：A 先現值單一來源、再成套V3戰鬥尺度；B 先只改鬥士表；C 只改狼象特性並保留混合尺度。建議A，B有停滯風險，C能小切但不能宣稱完成V3。main若已有授權，可直接補依據，不重問已定方向。

武器傷害與種族拳傷：可選來源傷害為固定總值，或基礎拳傷加武器增量／套倍率。建議先請使用者確認熊拳2持直劍傷1是否合理，再定統一公式，不由design自行假定；狼象加成在武器／虛弱／背擊之前或之後也須明示。

新尺度防禦／恢復：可維持現值觀察，或另提匹配10體力的新數值。建議成套提案並附戰局比較，現在不報一組未經試驗的數字。背擊可維持1.2或採字面2；建議先保留既有1.2並另決定小數傷害／取整策略，而非用2暗中補償round。倒地3秒可包含起身或另加起身；建議把受控總時間明確標出後讓使用者選。

豪豬／蛇可沿用快版差異或暫用V3標準模板；建議遷移時暫用標準、特性留白，但這是提案不是來源明定。恐懼N、無敵N、巨人速度-4單位、惠惠火石及變羊恢復等源稿空白維持待定，不用0或猜值填runtime。
