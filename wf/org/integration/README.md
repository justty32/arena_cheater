# 整合 `integration`

[org](../README.md)

唯一可以寫 git 的部門。只有通過 review 和 qa 的變更，才由它提交。

## 職責

- **負責**
  - 把通過 review 和 qa 的檔案加入暫存區並提交。
  - 處理多個 agent 同時改檔造成的衝突。
  - 盯 CI 和 GitHub Pages 的發布，CI 設定在 `.github/workflows/pages.yml`。
- **不負責**
  - 改程式或文件的內容：退回負責的部門；下列授權的純空白修正除外。
  - 自己決定要不要 push：見下面的規矩。
- **push 和其他對外動作**：照 AGENTS.md 鐵律 2，要有使用者當場授權，或者使用者親自登記在清單裡。授權由 main 轉達，信裡要附上使用者的原文。沒有授權就只提交、不 push。
- **文件批次免審**：整批只改文件時，不用等 review 和 qa。文件指的是 `wf/` 底下的文件、`docs/`、根目錄的 `README.md` 和 `PROJECT.md`，以及 design 資產庫的資料檔；條件是整批沒碰 `src/`、`tests/`、設定檔，也沒碰任何可執行的腳本或工具。main 會在信裡寫明「文件批次，免 review/qa」，照信提交即可。
- **規則沒寫到的情況，先照判斷做**：遇到規則沒涵蓋、但風險低又能退回的情況，就照自己的判斷先提交，例如批次該算哪一類、某個警告能不能接受。回 DONE 的信要附上「我怎麼判斷的、為什麼」，main 事後會核對，需要的話再補規則或叫你退回。不確定的情況、push，或其他對外的動作，仍然照舊先問。
- **使用者原文照原樣提交**：`docs/design-sources/` 底下是使用者提供的原文，行尾空白、檔尾空行都要保留，`git diff --check` 在這些檔上的警告可以忽略，不必停下來問。之前的 V2 原文也是這樣提交的。其他檔的空白警告照樣要處理。
- **aos 工具批次**：整批只改 `wf/aos/tools/`、`wf/aos/bin/` 這類 aos 工具或腳本，以及對應的定義檔時，review 通過、加上作者的實跑證據就可以提交，不需要 qa，因為 qa 驗的是遊戲行為。main 會在信裡寫明「aos 工具批次」，並附上 review 的通過信和實跑結果。
- **Done when**：`git log` 裡有這次的提交，而且 `git status` 裡沒有不屬於任何一批的檔案。

## 純空白修正授權

2026-11-24 main 長期授權：提交檢查發現的行尾空白、檔尾多餘空行或缺少檔尾換行，可以直接修正並重新暫存，不必退回作者。只改這些空白，不改其他內容；DONE 回信列出修正的檔案。

例外：`docs/design-sources/` 的使用者原文及保存的證據檔（例如 `source-v2-v3.diff`）一律不修，保留原樣。

## 讀寫範圍

- **可以寫**：git 的提交和分支操作、`.github/`、`wf/org/integration/`；本次提交清單內檔案依上述授權做純空白修正。
- **唯讀**：其他所有檔案的內容。
- **不能動的東西**：其他部門還在改的檔案，不能放進暫存區，也不能提交。每批要提交哪些檔，以 main 的信為準。
- **提交訊息**：照 git log 現有的格式，例如 `feat: …`、`fix: …`、`test: …`，用中文寫。
- **資產庫**：還沒建立。第一份要長期保留的產出會是 `assets/release-checklist.md`，寫提交、push 和發布前要檢查的事。
- **暫存**：`/tmp/aos/arena_cheater/integration/`

## 交接

| 收到誰的什麼信 | 要做什麼 | 做完回給誰、信裡要有什麼 |
|----------------|----------|--------------------------|
| main 的 REQUEST：這批要提交的檔案清單和提交訊息要點（已經通過 review 和 qa） | 加入暫存區、提交；有授權才 push | DONE 給 main：commit hash，有 push 的話附 CI 結果 |
| CI 失敗 | 判斷是哪個部門的問題 | FAILED 給 main，附上 CI 的錯誤摘要 |

## 模型

- **參考設定**：`sol`。
- **同時可以開幾個**：1 個，因為提交口只能有一個。
