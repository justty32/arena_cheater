# 信件格式：開工信和回信

[org](README.md)

部門之間怎麼寫信。這份是 2026-11-23 從第一輪的[回顧](../notes/investigations/org-retro-1/README.md)整理出來的。那一輪卡住，大多是開工信漏寫了規矩；回信則寫得太長，重點被埋掉了。

## 開工信（REQUEST）一定要寫的

| 欄位 | 寫什麼 |
|------|--------|
| 範圍和排他權 | 這次能寫哪些檔。哪些檔在這段期間歸你獨佔，別人不會動 |
| 基準 | 從哪個 commit 開始。驗收時拿什麼來比對 |
| 驗收分工 | 你自己要驗到哪裡，哪些交給別的部門驗 |
| 資源規矩 | 要不要拿 Node 鎖。能不能開伺服器、能不能試玩 |
| 預期的並行變動 | 這段期間還有誰在改哪些檔。一般規則見 org README 的「並行變動只看自己的範圍」 |
| Done when | 做到哪一步算完成，回信要附上什麼 |

如果做的是工具或 runner，開工信還要多寫一份**故障矩陣**：成功、一般失敗、逾時、取消、啟動中取消、清理失敗，以及之後的步驟還能不能跑，每一種情況各要怎麼處理。也要寫明哪些情況算阻擋，哪些只是已知限制，例如 SIGKILL、manager 故障。第二輪 review 審了三次才收斂，就是因為少了這張表。

不用每次重抄角色卡。信裡只寫這次跟角色卡不一樣的地方，也就是例外。

## 做事途中

- **長的工作，每到一個階段的交界就讀一次信**：例如做完一塊、要開始下一塊之前。這樣 main 寄來的取消或修改，才不會等整件事做完才看到。

## 回信的寫法

- **信要短**：信裡只寫狀態、對象、數量、耗時、卡在哪裡、產物放在哪。細節另外存成檔，例如逐案清單、完整 log、逐塊對照，信裡附上路徑。
- **in_reply_to 一次填對**：回覆原信時，第一封就填對 `in_reply_to`，不要先寄一封、再補一封。
- **分清楚是不是環境問題**：環境擋住了，例如缺系統函式庫、權限不夠，就回 BLOCKED，不要回 FAILED，就算測試 runner 顯示失敗也一樣。
- **未完成的要寫清楚**：沒跑的、不能跑的、不適用的，三種分開寫。
