# PD10 作弊經濟拆解實跑證據

[dev](../../README.md)｜[分析計畫](../../../design/assets/audits/pd10-2026-11-25/README.md)

## 範圍與結論

本批只在隔離副本加入量測，正式 src、tests 與數值均未改動。四組各 seed 1..100，支持狼、原生裸裝起手、dt=1/30；無注入牌石、無換石、無調整時限。結果供 design 判讀 PD10，不替真人玩法或經濟改版作決定。

新版直接政策的 3664 個可介入窗口，2852（77.84%）沒有政策允許的牌；395（10.78%）為總石不足，409（11.16%）為指定色不足，成功 8（0.22%）。故不能把未成功全稱為缺石。全牌政策能解除很多牌型限制，但仍有反覆卡色；成功出牌不代表有效傷害或真人趣味。

同 seed、兩版本都能介入的窗口交集：直接政策兩版均 279 窗口／7 次成功，全牌均 287／264。不能從新版累積失敗較多直接判定經濟退化，也不能由配對總數相同證明經濟完全無問題。版本整體比較無法單獨辨識一個戰鬥參數的因果效果。

## 版本與原生經濟

舊版 `7d9b7bbc621e3bb2728fe02154cb78adcdd77992`；新版 `03b15e1f05ad5701f6c47f7fb7fcc62460c39cfd`，不是執行當下 HEAD。

兩版原生 card-catalog.ts、resources.ts、engine-cards.ts 無 diff。18 種牌各兩張；起手 3 牌、3 石，成功出牌補 2 石、支持者擊殺補 3 石；費用、思考及直覺規則相同。原生時限舊 180 秒、新 300 秒，戰鬥及終局規則不同。原生來源快照見 native-sources/，修補差異見兩份 instrumentation.patch；manifest.json 保存 SHA256。

## 全局、早期與配對

每組均 100 局。以下依序為「窗口／成功／無政策牌／總石不足／色不足；成功局數」：

- 新直接：3664／8／2852／395／409；8 局（92 局未成功）。
- 舊直接：279／7／216／31／25；7 局（93 局未成功）。
- 新全牌：3167／1984／0／0／1183；94 局（6 局未成功）。
- 舊全牌：287／264／0／0／23；93 局（7 局未成功）。

共同早期 scheduled<=180：新直接 3256／8／2540／363／345；新全牌 2851／1868／0／0／983；舊版等於全局。早期不是同樣暴露時長，仍要另看配對。

配對依每 seed 的 executed scheduled 交集，不只截斷在 180 秒：直接兩版均 7 成功、216 無牌；新版總石 33／色 23，舊版總石 31／色 25。全牌兩版均 264 成功／23 色不足。直接各有 7 局、全牌各有 93 局在配對窗口成功。新版多的一次直接成功在舊版已不能介入後。

沒有合法政策目標、冷卻及其他主因均為零；候選目標搜尋用盡計數亦為零。程式沒有出牌冷卻，不拿換石冷卻充數。逐牌多條件診斷仍保留在外部 raw（路徑見證據節），不只存互斥主因。

## 收入、時間與反覆卡色

四組初始均 300 石。依「成功補石／支持殺補石／付款石」：新直接 16／81／8；舊直接 14／60／7；新全牌 3968／129／3426；舊全牌 528／102／421。逐色收入、付款與末態見各 summary，逐事件前後庫存見 raw；全部逐事件及末態對帳通過，無其他收入支出。低費牌與成功補石形成循環，不能把 1984 次成功當作 1984 次有效傷害。

平均戰長新直接 255.078 秒、舊直接 27.916 秒、新全牌 228.901 秒、舊全牌 27.656 秒。平均狼可介入時長依序 185.614、16.089、160.910、16.477 秒；定義為狼死亡、原生終場、原生時限的最小值，是時長上限，不保證每一幀都可出牌。清算、死亡與終局不算失敗窗口，所有預定但未執行窗口保留 skipReason。

首次支持者擊殺發生／未發生局數與發生者中位時間：新直接 23／77、102.467 秒；舊直接 8／92、15.833 秒；新全牌 35／65、88.233 秒；舊全牌 19／81、15.200 秒。支持殺補石時點在新版延後，但原生補石參數沒有改；全局收入總數也受暴露時長及戰鬥差異影響。支持殺間隔中位數依序 137.967、7.667、45.783、7.200 秒，僅對實際相鄰支持殺事件計算，不能代表所有局。

新全牌首次成功 94 局，中位 5 秒、平均 6.064 秒、最晚 105 秒；六局未成功。1183 個色不足窗口分布於 60 局，其中 52 局最後一個可執行窗口仍為色不足，不是 1183 個獨立失敗樣本。零成功 seed 為 9、20、28、29、46、61，可執行窗口依序 36、45、39、36、38、22。其首末手牌與五色石、每局尾端連續卡色長度，完整列在 new-all-blocking-detail.json。六局手牌皆未變；seed 9 有支持殺補石但仍未成功，其餘五局首末石庫存不變。因此全牌也存在未啟動與持續卡色，不能宣稱經濟沒有問題。

## 政策與診斷契約

首次 scheduled=5，之後每 5 遊戲秒一窗口；先 advance，再執行到期窗口，每窗口最多成功一張。狼死亡、finished、清算或非 running 跳過；思考選揭示候選 index 0 並經 API 恢復 running，不額外送窗口。

直接政策僅 lightning、lightning-rain、divine-wrath；依手牌順序選首張可支付且合法者。目標活熊優先，其他活敵依精確 hp/maxHp 降序，同分初始順序；只取首要敵人，範圍牌用該敵中心。

全牌依手牌順序；即使先找到可出牌，仍診斷其餘手牌。治療先受傷狼，再其他活鬥士缺血比例降序；增益先狼再初始順序；傷害及負面先依敵人順序。裝備先狼中心、其他活鬥士初始順序中心，再格點；投擲消耗品與陷阱先敵中心，再其他活鬥士中心、格點。重複座標去重保留首次。有限搜尋用盡只表示政策候選無解，不代表連續場地無解。

格點間距 1m，y 外圈升序、x 內圈升序，保留 x²+y²<=ARENA_RADIUS²；實際原生半徑 7.5，177 點，座標極值 -7..7。runner 由原生半徑生成，與計畫 -8..8 篩圓後的點集及順序相同（邊界 ±8 不會入圓）。各組 raw.grid.points 保存完整點集。

原生 findPayment、validateCardPlay、playCard 決定付款及成功。目標合法性另外以唯讀幾何／血量診斷，因 API 可能先回支付失敗；保留原始 apiReason，候選檢查至首個合法目標或用盡。互斥主因順序為成功、無政策牌、全無合法候選、冷卻、合法候選全總石不足、至少一張總數夠但色不足、其他；每張牌的獨立 target/total/color 條件全部保留。

## 證據、修正與重現

原始資料不在 repo：原 raw/ 已依 main 要求整個搬至 `/tmp/aos/arena_cheater/dev/pd10-2026-11-25-raw/`，未刪除。下文的 raw 指該外部目錄；暫存可能在清理或重開機時遺失，並非永久備份。manifest.json 保留原始邏輯路徑、每檔 SHA256 與實際 externalPath，inRepo=false 明示未隨 repo 保存；runner、插樁、原生版本與重建腳本仍留在 repo。

外部 raw 為四組完整逐局／逐窗口／收支與死亡時間線，另保留兩直接組初版。四份 summary 含全局、早期、逐牌成功、逐局值、首次成功／死亡／支持殺、間隔、狼死亡、勝負及缺失樣本數；comparisons.json 含逐 seed 配對差異。大型表採 wf-table/1；物件型摘要內嵌逐局表。JSON 請按欄位或 tabledb 查詢，不整份載入對話。

收入來源最初由事件鄰接推斷；新全牌首次執行在法術擊殺交錯時觸發來源斷言，是量測 bug，不是產品 bug。修正為 drawStones 原生呼叫點直接標記 initial／successful-play／supported-kill，不改 RNG 或付款順序。四組最終均用修正版；兩直接組重跑除 income.source 外，所有窗口、戰長、終局與事件欄位完全相同，見 runner-equivalence.json。失敗、鎖超時與重跑 verify 全保留在 verification/。

四組最終 verify 分別為 new-direct-source-fix/verify-jdkp4wlm、old-direct-source-fix/verify-fajuc6g0、new-all-source-fix/verify-ueoe5tj2、old-all/verify-fy5oq_64，test/build 均 exit 0、scope_cleaned=true。stop_exit_code=5 伴隨 inactive/not-found 是完成後 scope 已不存在，非殘留程序。僅隔離量測 runner 一案，並非重跑正式完整核心測試，也未執行 E2E；正式遊戲程式未改動。

重現：在專案根目錄將本目錄 prepare.py、runner.test.ts 放到全新的 `/tmp/aos/arena_cheater/dev/pd10-2026-11-25/`（若已有歷史副本，先另行保留，不覆寫）。以 Python 執行 prepare.py，從兩 revision git archive 建副本、套只讀插樁、移除副本內原測試並安裝 runner、連結既有 node_modules，檢查專案設定一致。依分組修改副本 pd10-config.json 的 policy 為 direct 或 all，依原順序逐組呼叫 arena_verify(step=all, workspace=副本, timeout_s=300, lock_timeout_s=180)，不得直接跑 Node、不得並行。all 政策結果檔不會被 direct 覆寫。完成後在同暫存根執行 summarize.py 產摘要與配對。reproduction-check.json 證明更新後 prepare 可重建與最終驗證副本完全相同的插樁檔及 runner（Python 重建比對，不額外跑 Node）。

本輪不建議直接修改數值；若需後續測起手、色石取得或循環機制，應由 design 列互斥可測選項、使用者決定方向，避免同時混入換石政策與經濟改動。
