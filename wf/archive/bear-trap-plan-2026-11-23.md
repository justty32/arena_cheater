## 交付與封存紀錄

依 main 交接，兩批 review 通過，`arena_verify` 核心 162 項及 build 通過，qa E2E 25 項全過；固定 seed 定向真 UI 完整對局覆蓋桌面與 320／390 px。design 本輪只同步文件，沒有重跑工程驗證。

main 已看截圖，真人趣味、停追／反擊畫面、刺洞並排辨識與自然抽牌頻率仍未驗。地上夾子偏小及腳部遮擋列為後續候選，不在本輪修改。封存表示本輪工程切片已交付，不表示主觀趣味、平衡或全部原計畫人工驗收已通過。現行行為及驗證邊界以產品文件與規格為準。

## 第一步：卡牌與狀態邊界

dev 先核對 `src/arena/README.md` 與目前分支程式，確認 QA 拆分 E2E 的變動，避免重建舊測試檔。由 main 在開工信指定基準 commit、可寫路徑及與 qa 的測試排他權。

在 `model.ts` 加捕獸夾卡種、可區別的陷阱種類與定身截止狀態；名稱識別字由 dev 決定。定身應能與 attack／airborne／fallen 等姿態共存，不用單一姿態覆蓋它們。`engine-cards.ts` 牌庫若自動取卡牌表就不必另改生成流程；只加入規定的兩張牌，不改支付與補給契約。`engine-items.ts` 將新牌接到共用地面驗證、付款與布置流程。

先補牌庫與付款核心案例：合法施放只消耗一次，正常補兩石一牌；錯付、多付、缺額、場外、取消與錯誤階段不改狀態或 RNG；空地合法。抽乾回收後仍保持每種牌實例守恆，不硬編原先總牌數為永遠不變。

## 第二步：擴充陷阱而不改壞刺洞

在 `engine-traps.ts` 共用武裝、壽命、掃掠及接觸排序，按陷阱類型分派觸發結果；若更名既有 spike-pit 函式，同步 `engine.ts` 接線。先扣生命，再只對生還者刷新定身。保留先放先處理、接觸時間最早者優先、同時接觸固定 id 排序及原到期邊界。

核心測試涵蓋武裝前／恰好武裝、到期前／恰好到期、圈內／邊界／圈外、單步穿越、同陷阱兩人、同位置多陷阱、刺洞與捕獸夾混用。驗證支持者也可踩、死者不踩、空中跨越不踩、落地可踩，以及第一個陷阱殺死目標後後續陷阱不能再次命中死者。確認零陣營傷害歸屬、不授予擊殺補石／狼特性。

## 第三步：只限制自主移動

主要修改 `engine-combat.ts`，必要時由 `engine-damage.ts` 處理死亡／狀態清理。不得在整段 `act` 開頭以定身為由提早 return：這會一併凍結體力恢復、控制到期、攻擊命中及防禦。限制應落在自主平移路徑，而非整個角色更新。

核心測試分開建立可攻擊與不可追擊的情境，避免把「AI 正在選遠處裝備」誤判為定身禁止攻擊。覆蓋近戰及弓在範圍內仍可出手、已準備攻擊正常命中、轉向、防禦耗體與恢復照常；無目標在射程時不能追擊，也不能走向裝備，但身旁裝備仍依既有規則拾取。

另驗證首次三秒、到期邊界、重中刷新不累加且仍扣傷害；被擊飛、跌倒、起身時保留既有控制優先序，三秒照常倒數。角色分離及場界修正仍生效，不能以座標完全不動斷言定身。死亡後到期不復活，重開沒有殘留定身。測試以遊戲時間推進，固定步進誤差與規格一致。

## 第四步：呈現與生命週期整合

在 `view.ts` 區分兩種陷阱及武裝狀態，為受困鬥士增加不覆蓋動作的提示；`layout.ts`／`hand-view.ts` 顯示卡面、費用與效果，`fighter-details.ts` 顯示定身。只有既有資料接線不足時才動 `card-actions.ts` 或 `arena-hud.ts`，不另改輸入手勢。陷阱不是投送，不污染最近投送摘要。

整合案例確認暫停布置後沒有飛行等待、付款立即完成，但武裝、壽命與定身倒數不變；恢復後按遊戲時間前進。重試同場及新局清空；定身和未觸發陷阱不拖延結算，待在途攻擊結算時不再接受布置。相同 seed／指令／時間序列結果一致，倍速等價；保留刺洞、擊飛與經典模式回歸。

## 第五步：工程驗證與 qa 交接

dev 補核心測試，建議獨立陷阱測試檔或沿現有陷阱案例擴充，由 dev 決定最小合理落點並更新測試導航。透過 `arena_verify` 跑核心與建置，交回實際指令、結果與 log 路徑；不能只靠 build。不要在本輪改其他遊戲數值修飾試玩結果。

qa 以 `arena_e2e` 跑完整回歸；測試工具會取 Node 鎖與資源限制，不另外並行開未受控 Node 工作。需要瀏覽器時用獨立埠，避免接到工作區已有伺服器。main 協調 dev／qa 不同時修改同一 E2E 檔。

新增代表性的桌面流程：取得可付捕獸夾、暫停放置、核對一次付款及布置、等待牆鐘確認仍凍結、恢復後觸發與顯示定身、解除後恢復自主移動、重試清空。手機流程覆蓋點牌／點地、觸控預覽與捲動取消、付款提示；沿用既有拖曳／Esc 回歸，不為每張牌複製所有通用案例。核心負責精確傷害／排序／三秒邊界，E2E 不用 DOM 文字冒充模擬證據。

qa 真 UI 另試一場有捕獸夾介入的完整戰鬥，觀察追擊者停下但可近身反擊、支持者也會踩、陷阱與刺洞可辨識，並檢視桌面及 320／390 px 窄屏的場地、三牌、石盤與提示。針對定向測試可以使用固定 seed／測試 fixture，但試玩自然抽牌時另記是否拿到牌、是否有機會布置；不能將定向必得牌當成實際出現頻率。

試玩回報將操作可完成、狀態可讀性與戰術趣味分開標示通過／待調。未遇到某交互就標未驗，不靠一場戰鬥宣告平衡完成。

## 收尾與完成定義

review 核對定身限制的落點、同 tick／死亡／暫停語義及測試反例。QA 或 review 發現問題由 main 退回 dev；主觀平衡建議交 design，不直接更動授權規格。

核心、建置、E2E 與真 UI 證據齊備且阻擋問題解除後，dev／qa 寄信請 design 同步 PROJECT、戰鬥原型文件、需求記錄與 roadmap。程式新檔或職責改動同步 code map 與測試導航，超出部門範圍請 main 協調。integration 才執行 git 提交；本計畫不授權 push。全部實作完成後才處理計畫封存，不以本輪文件交付當成實作完成。
