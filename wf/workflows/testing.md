# testing — 驗證

[WORKFLOWS](../WORKFLOWS.md)｜[INDEX](../INDEX.md)

**何時用**：修改後驗證、重構前記錄基準，或使用者要求測試。
**何時不用**：環境問題走 [dev-env](dev-env.md)，失敗原因調查走 [investigation](investigation.md)。

## 目前可驗證範圍

目前僅有文件與工作流，沒有遊戲程式、測試套件或 npm scripts，不得宣稱遊戲已通過測試或可啟動。

| 驗證 | 方法 | 誰跑 |
|------|------|------|
| 文件驗證（改完必跑） | 確認相對連結目標存在、導航一致、提案與已實作狀態分開 | agent |
| 導入驗收（本輪） | 搜尋 Markdown 中的未填佔位、模板說明與導入判斷，全部清除 | agent |
| 工作流 lint（選用） | `bash wf/tools/wf-lint.sh --strict .`；使用者要求時才跑 | agent |
| 遊戲測試、型別檢查、建置 | 尚未建立；第一個可執行切片落地時補上實測指令 | agent |

## 後續遊戲驗證原則

對自動戰鬥與作弊機制，測試應觀察實際狀態轉換與結果，例如無效目標是否拒絕且不扣資源、作弊是否影響戰局、偵測與懲罰是否按規則結算。隨機與時間若納入模擬，需要可控制的 seed 與步進，以重現失敗。

介面落地後，再測從開局、介入到結算的完整操作；未做瀏覽器驗證時明確回報限制。新增驗證器需以一個應失敗與一個應成功的輸入確認它確實能擋錯；文件修正不另造鏡像測試。

## Done when

適用的文件驗證已完成；程式實作後則要求對應測試／建置通過並更新本表。未跑、不可跑與不適用要分開記錄；只有確實必須由使用者處理的阻礙才寫入 [WAIT_USER](../WAIT_USER.md)。
